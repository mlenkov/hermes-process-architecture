# ADR-002: Рефакторинг структуры выходных файлов

**Статус:** Предложен (ожидает утверждения)
**Дата:** 2026-07-30
**Автор:** architect

---

## Проблема 1: Избыточный `_meta.yaml`

Каждый навык создаёт два файла в одной директории: сам артефакт (например, `process-regulation.yaml`) и `_meta.yaml`. При этом `_meta.yaml` дублирует информацию из ключа `meta:` основного файла:

| Поле | `_meta.yaml` | `meta:` в артефакте |
|------|:---:|:---:|
| `artifact_id` | ✅ | `artifact` ✅ |
| `tf` | ✅ | `tf` ✅ |
| `la` | ✅ | `la` ✅ |
| `generated_by` | ✅ | `generated_by` ✅ |
| `timestamp` | ✅ | `timestamp` ✅ |
| `sources_read` | ✅ | `quality.sources_read` ✅ |
| `schema_valid` | ✅ | `quality.schema_valid` ✅ |

**Последствия:**
- DRY нарушен — 100% полей дублируются
- При изменении одного файла второй рассинхронизируется
- 20 лишних файлов в `outputs/07.007/` (10 _meta.yaml в А-01.6 + 3 в D-01.7 + остальные)

**Решение:** Полностью удалить `_meta.yaml` из архитектуры. Вся метаинформация хранится в `meta:` ключе артефакта.

## Проблема 2: Глубокая вложенность директорий

Текущая структура создаёт 4 уровня вложенности для одного файла:

```
outputs/07.007/А/А-01.6/la-001/process-info-context.yaml
└── 07.007 ── А ── А-01.6 ── la-001 ── file.yaml
               ^  ^         ^
               |  1 уровень 2 уровень
               блок         TF        LA
```

### Дополнительная проблема: Несогласованность внутри D-блока

В D-блоке используются **две разные схемы** именования:

| Путь | Схема | Кол-во файлов |
|------|-------|:-------------:|
| `D/01.7/la-001/` | Только номер ТФ | 4 (от td-gen до рефакторинга) |
| `D/D-01.7/la-001/` | Буква + номер ТФ | 18 (основные артефакты) |
| `D/D-01.7/inputs/` | Отдельная папка inputs | 2 |

**Факт:** `01.7` и `D-01.7` — это одна и та же ТФ, но данные разбросаны по двум разным путям.

## Варианты решения

### Вариант A: Плоская структура (один файл = один путь)

```
outputs/07.007/
├── A-01.6-info-context.yaml
├── A-02.6-regulation.yaml
├── B-01.6-crossfunction-analysis.yaml
├── C-01.7-maturity-assessment.yaml
├── C-02.7-architecture-roadmap.yaml
├── D-01.7-stakeholder-mapping.yaml
├── D-02.7-architecture-designed.yaml
├── D-03.7-transformation-plan.yaml
├── D-04.7-methodology-developed.yaml
├── labor-function-to-skill-mapping.yaml
├── labor-coverage-registry.yaml
└── pdca-reports/
    └── pdca-2026-07-30.yaml
```

**Плюсы:**
- Минимальная вложенность (0–1 уровень)
- Полное имя файла самодокументируется (блок + ТФ + суть)
- Один взгляд — вся структура видна

**Минусы:**
- 18 ТФ × 5–10 LA = до 180 файлов в одной директории — навигация ухудшится
- Нет группировки по блокам — `B-01.6` и `B-01.6` не рядом
- Непонятно, где inputs (не LA, а внешние данные)
- Полная миграция: все td-gen, executor, seeder нужно переписывать
- Латинская `A` не совпадает с кириллической `А` в профстандарте

---

### Вариант B: Группировка по блокам (один уровень вложенности)

```
outputs/07.007/
├── block-A/
│   ├── A-01.6-info-context.yaml
│   ├── A-02.6-regulation.yaml
│   ├── A-03.6-deployment-plan.yaml
│   └── A-04.6-pdca-report.yaml
├── block-B/
│   ├── B-01.6-crossfunction-analysis.yaml
│   ├── B-02.6-crossfunction-model.yaml
│   ├── B-03.6-crossfunction-spec.yaml
│   ├── B-04.6-crossfunction-deployment.yaml
│   └── B-05.6-crossfunction-audit.yaml
├── block-C/
│   ├── C-01.7-maturity-assessment.yaml
│   ├── C-02.7-roadmap.yaml
│   ├── C-03.7-project-charter.yaml
│   ├── C-04.7-system-audit.yaml
│   └── C-05.7-deviation-report.yaml
├── block-D/
│   ├── D-01.7-stakeholder-mapping.yaml
│   ├── D-02.7-architecture-designed.yaml
│   ├── D-03.7-transformation-plan.yaml
│   └── D-04.7-methodology-developed.yaml
├── labor-function-to-skill-mapping.yaml
├── labor-coverage-registry.yaml
└── pdca-reports/
    └── pdca-2026-07-30.yaml
```

**Плюсы:**
- 1 уровень вложенности (всего 2 от `outputs/`)
- Группировка по блокам — логически связано лежит рядом
- Один артефакт = один файл (нет LA, нет _meta.yaml)
- Имя файла содержит ТФ + суть (человекочитаемо)
- Легко найти все артефакты блока — `ls block-B/`
- Латинские `A`,`B`,`C`,`D` (нет путаницы с кириллицей)

**Минусы:**
- Каждый новый LA — отдельный файл (10 LA А/01.6 → 10 файлов)
- Но это нормально: `A-01.6-info-context.yaml`, `A-01.6-info-context-la002.yaml` и т.д.
- Миграция: нужно переименовать ~40 файлов + обновить executor/seeder

## Дополнительная проблема: Кириллическая `А`

В текущей структуре используется кириллическая `А` (U+0410) для блока A, что вызывает:
- Конфликты с латинской `A` (U+0041) — визуально неразличимы
- Проблемы в shell-скриптах и поиске (`find outputs/07.007/А/` vs `/A/`)
- Невозможность набрать с клавиатуры (нужно копировать)

**Решение при любом варианте:** Использовать только латинские `A`, `B`, `C`, `D`.

## Рекомендация: Вариант B с LA-суффиксом

**Выбран:** Вариант B (группировка по блокам) с уточнением для множественных LA.

### Схема именования

```
outputs/07.007/
├── block-A/
│   ├── A-01.6-info-context.yaml           ← la-001 (основной артефакт)
│   ├── A-01.6-info-context-la002.yaml     ← la-002 (если есть)
│   └── A-02.6-regulation.yaml
├── block-B/
│   └── B-01.6-crossfunction-analysis.yaml
├── block-C/
├── block-D/
│   ├── D-01.7-stakeholder-mapping.yaml    ← из D/01.7/la-001/
│   ├── D-02.7-architecture-designed.yaml
│   └── ...
├── labor-function-to-skill-mapping.yaml
├── labor-coverage-registry.yaml
├── monitor/                               ← остаётся как есть
│   └── 20260729_*.yaml
└── pdca-reports/                          ← остаётся как есть
    └── pdca-2026-07-30.yaml
```

### Обоснование выбора

1. **Совместимость с kanban:** В kanban 26 задач для D-блока. Они ссылаются на файлы по старым путям. Вариант A (плоская) требует полной миграции всех ссылок. Вариант B позволяет сделать phased rollout: сначала мигрировать блок A (новые навыки), потом B, C, D — каждый раз обновляя kanban-ссылки для одного блока.

2. **Человекочитаемость:** `A-02.6-regulation.yaml` понятнее, чем `А/А-02.6/la-001/process-regulation.yaml`.

3. **Масштабирование:** 5 блоков × 3–4 файла = ~20 файлов на блок — директория не перегружена.

4. **Inputs:** Внешние данные (не LA) хранятся в `inputs/` внутри блока:
   ```
   block-D/
   ├── inputs/
   │   ├── architecture-current.yaml
   │   └── business-strategy.yaml
   └── D-01.7-stakeholder-mapping.yaml
   ```

5. **Обратная совместимость:** Старые пути не удаляются сразу — добавляются симлинки `А/ → block-A/`, `D/01.7/la-001/stakeholder-mapping-schema.yaml → block-D/D-01.7-stakeholder-mapping.yaml`. Через 1 PDCA-цикл старые пути удаляются.

6. **Исключение LA из пути:** LA-суффикс добавляется только если есть несколько артефактов для одной ТФ (`la-001` не пишем — подразумевается по умолчанию; `la-002+` добавляем суффикс `-la002`).

### План миграции

| Фаза | Что делаем | Затрагивает |
|:----:|-----------|:-----------:|
| 0 | Утверждение ADR-002 | — |
| 1 | Обновить `new-skill-architecture-blueprint.md`: удалить `_meta.yaml`, новая структура | 1 файл |
| 2 | Обновить `architect-info-gatherer/SKILL.md`: удалить `_meta.yaml`, новый output_path | 1 файл |
| 3 | Обновить `architect-regulation-writer/SKILL.md`: удалить `_meta.yaml`, новый output_path | 1 файл |
| 4 | Удалить `_meta.yaml` из outputs (A-01.6, A-02.6) | 11 файлов |
| 5 | Переместить A-блок: `А/А-01.6/la-*/ → block-A/A-01.6-*-la*.yaml` | ~10 файлов |
| 6 | Переместить D-блок: `D/01.7/*, D/D-*/*/ → block-D/D-*.yaml` | ~22 файла |
| 7 | Обновить `architect-executor/SKILL.md`: новый `output_dir` resolver | 1 файл |
| 8 | Обновить `architect-seeder/SKILL.md`: новые пути для pipeline | 1 файл |
| 9 | Создать симлинки для обратной совместимости | ~30 ссылок |
| 10 | Обновить kanban-задачи (ссылки на файлы) | 26 задач |

---

## Принятые решения (для реализации)

1. **`_meta.yaml` удаляется полностью.** Все meta-поля — внутри `meta:` ключа артефакта.
2. **Новая структура:** `outputs/07.007/block-X/X-XX.X-name[-laXXX].yaml`.
3. **Латинские буквы** `A`, `B`, `C`, `D` (не кириллица).
4. **По умолчанию LA-001** — не пишется в имени. LA-002+ — суффикс `-la002`.
5. **Inputs** — внутри блока: `block-X/inputs/filename.yaml`.
6. **Phased rollout:** блок за блоком, начиная с A.
7. **Симлинки** для обратной совместимости на 1 PDCA-цикл.
